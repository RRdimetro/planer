# Измерения производительности — Linux, RC

Использован один и тот же синтетический, изолированный SQLite fixture: 1000 видимых задач, 3000 исторических завершений и 3000 сессий. Сравнение фактической сборки 0.3.0 с текущим RC. CPU: INTEL(R) XEON(R) PLATINUM 8573C. Никаких пользовательских баз/демонстрационных KPI в пользовательском режиме.

Три новых Electron-процесса, тёплый файловый кеш, ожидание шрифтов и двух animation frames, включены Playwright/debug накладные расходы. Это не замер старта после перезагрузки Windows. Median startup: **5531 → 1604 ms**. Исходные серии: [7789, 5111, 5531] → [1604, 1525, 1624].

Переходы измерены по одному разу; статистической значимости и улучшения каждой страницы не заявляем. Список задач в этом прогоне медленнее; остаётся виртуализованным: 14 DOM-строк при 1000 записях, поиск 55→53 ms. Планировщик после устранения повторной сортировки lanes вернулся к исходному времени. Суммарный process working set в точке измерения: 718→641 MiB; сумма отдельных пиков не является одновременным пиком приложения. Запущены отключённые GPU/анимации, по этим данным нельзя утверждать 60fps.

Главные исправления: повторное использование Intl.DateTimeFormat, кеш local day для timestamps, один проход по сессиям вместо многократных фильтров, виртуализация истории фокуса, кеширование календарных lanes на день. Renderer errors: 0, SQLite integrity: ok. Windows performance **не измерен**.

JSON с сырыми данными: `performance/baseline.json`, `performance/after.json`; повтор: `DISPLAY=:102 node scripts/rc-performance.mjs after` после production build. Все fixture-каталоги создаются в OS temp.
